# ドメイン文書

エンジニアリングスキルがコードベースを調査するときに、このリポジトリのドメイン文書を利用するための規約です。

## 調査前に読む文書

- リポジトリ直下の **`CONTEXT.md`**、または
- リポジトリ直下に存在する場合は **`CONTEXT-MAP.md`**。各コンテキストの `CONTEXT.md` を指すため、調査対象に関係するものを読みます。
- **`docs/adr/`**。作業対象に関係するADRを読みます。複数コンテキストのリポジトリでは、コンテキスト固有の決定を記録した `src/<コンテキスト>/docs/adr/` も確認します。

これらのファイルが存在しない場合は、指摘や事前の作成提案をせず、そのまま作業を続けます。`/grill-with-docs` や `/improve-codebase-architecture` から呼び出される `/domain-modeling` が、用語や決定事項の確定時に必要な文書を作成します。

## ファイル構成

このリポジトリでは、次の単一コンテキスト構成を使用します。

```text
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

複数コンテキスト構成では、リポジトリ直下の `CONTEXT-MAP.md` を目印とし、次のように配置します。

```text
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← システム全体の決定
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← コンテキスト固有の決定
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 用語集の語彙を使用する

Issueの件名、リファクタリング案、仮説、テスト名などでドメイン概念に名前を付ける場合は、`CONTEXT.md` で定義された用語を使用します。用語集が明示的に避けている同義語へ置き換えないでください。

必要な概念が用語集に存在しない場合は、プロジェクトで使われていない言葉を持ち込もうとしていないか再検討します。実際に用語が不足している場合は、`/domain-modeling` で扱う課題として記録します。
